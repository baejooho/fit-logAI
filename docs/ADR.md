# FitLog AI — ADR (Architecture Decision Record)

본 문서는 프로젝트 진행 중 내린 주요 아키텍처 의사결정과 그 배경을 기록한다.

---

## ADR-1: AI API로 Gemini API 선택

### 상태
승인됨

### 배경 (Context)
프로젝트 초기에는 Claude API를 고려했으나, Claude API는 사용량 기반
유료 과금 방식이며 별도 결제수단 등록이 필요했다. 학습용 프로젝트로
무료 한도 내에서 충분히 동작할 대안이 필요했다.

### 결정 (Decision)
Google AI Studio에서 무료로 발급 가능한 Gemini API
(`gemini-2.0-flash` 모델)를 사용하기로 결정했다.

### 이유 (Rationale)
- 카드 등록 없이 즉시 API 키 발급 가능
- 무료 티어로 데모 및 개발에 충분한 호출량 제공
- JSON 형식 응답 생성 등 핵심 요구사항을 동일하게 충족

### 결과 (Consequences)
- API 호출 비용 부담 없이 개발 및 데모 진행 가능
- 추후 Claude API 등 다른 LLM으로 교체가 필요할 경우, 프롬프트
  빌더와 AI 호출 모듈이 분리되어 있어 교체 비용이 낮음

## ADR-2: 4주 플랜 일괄 생성 대신 1주 루틴 생성 방식 선택

### 상태
승인됨

### 배경 (Context)
초기 설계에서는 AI가 4주 점진적 과부하 플랜을 한 번에 생성하는 방식을
고려했다. 그러나 4주치 분량을 한 번에 생성하면 응답 토큰 수가 커지고,
무료 API 티어의 호출당 토큰 제한 및 속도 제한에 영향을 줄 수 있었다.

### 결정 (Decision)
AI 호출 1회당 1주 분량의 점진적 과부하 루틴을 생성하도록 설계했다.

### 이유 (Rationale)
- 응답 토큰 수를 줄여 API 제한 내에서 안정적으로 동작
- 응답 속도가 빨라져 사용자 경험(데모 포함) 개선
- 1주 단위 생성 구조는 추후 "다음 주 루틴 생성"을 반복 호출하는
  방식으로 자연스럽게 확장 가능

### 결과 (Consequences)
- 현재 버전은 4주 전체 플랜을 한 번에 제공하지 않음
- 향후 확장 시, 이전 주차 결과를 프롬프트에 포함시켜 점진적 과부하를
  여러 주에 걸쳐 반영하는 구조로 발전 가능 (PLANNING.md의
  향후 확장 계획 참고)

## ADR-3: SQLite 등 DB 제거, Stateless 구조 선택

### 상태
승인됨

### 배경 (Context)
초기 설계에서는 SQLite를 사용해 생성된 루틴과 사용자 기록을 저장하는
기능을 포함했다. 그러나 짧은 개발 기간 내에 DB 스키마, 저장/조회
로직까지 안정적으로 구현 및 검증하기에는 시간이 부족했고, 핵심
가치(AI 기반 루틴 생성)의 완성도를 우선해야 했다.

### 결정 (Decision)
현재 버전에서는 DB를 제거하고, 매 요청마다 입력값을 받아 AI 응답을
생성하여 화면에만 표시하는 stateless 구조로 설계했다.

### 이유 (Rationale)
- 핵심 기능(AI 루틴 생성)의 완성도와 안정성에 집중 가능
- DB 연동 관련 버그/설정 이슈로 인한 데모 리스크 제거
- Express + AI 호출만으로 구성되어 배포 및 환경 설정이 단순함

### 결과 (Consequences)
- 현재 버전은 생성된 루틴을 영구 저장하거나 이력 조회를 제공하지 않음
- 향후 SQLite(또는 다른 DB) 도입 시, Render 단계 이후에 저장 로직을
  추가하는 방식으로 확장 가능 (ARCHITECTURE.md의 향후 확장 시
  아키텍처 변화 참고)
