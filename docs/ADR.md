# FitLog AI — ADR (Architecture Decision Record)

본 문서는 프로젝트 진행 중 내린 주요 아키텍처 의사결정과 그 배경을 기록한다.

---

## ADR-1: AI API로 Gemini API 선택

### 상태
승인됨

### 배경 (Context)
유료 LLM API는 사용량 기반 과금 및 결제수단 등록이 필요해 학습용
1인 프로젝트에는 부담이 있었다.

### 결정 (Decision)
Google AI Studio에서 무료로 발급 가능한 Gemini API
(`gemini-2.5-flash` 모델)를 사용하기로 결정했다.

### 이유 (Rationale)
- 카드 등록 없이 즉시 API 키 발급 가능
- 무료 티어로 개발 및 데모에 충분한 호출량 제공
- JSON 형식 응답 생성 등 핵심 요구사항 충족

### 결과 (Consequences)
- API 호출 비용 부담 없이 개발 및 데모 진행 가능
- AI 호출 모듈(claude.ts)이 분리되어 있어 다른 LLM으로 교체 시 영향 최소화
- 503(Service Unavailable) 등 일시적 오류는 Google 서버 측 이슈로,
  재시도로 대응 가능함을 확인

## ADR-2: 4주 플랜 일괄 생성 대신 1주 루틴 생성 + 점진적 과부하 피드백 루프

### 상태
승인됨

### 배경 (Context)
4주치 플랜을 한 번에 생성하면 응답 토큰 수가 커지고, 무료 API 티어의
호출당 토큰 제한에 영향을 줄 수 있었다. 또한 실제 수행 결과(무게)를
반영하지 않은 장기 플랜은 현실성이 떨어진다.

### 결정 (Decision)
AI 호출 1회당 1주 분량의 루틴을 생성하고, 사용자가 기록한 수행 무게를
다음 주 루틴 생성 시 프롬프트에 포함하여 점진적 과부하를 반영한다.

### 이유 (Rationale)
- 응답 토큰 수를 줄여 API 제한 내에서 안정적으로 동작
- 실제 수행 무게 기록을 기반으로 한 점진적 과부하가, 사전에 고정된
  4주 플랜보다 현실적
- 매주 목표/경험/부위 등 입력값을 재설정할 수 있어 유연성 확보

### 결과 (Consequences)
- 1주 단위 생성 + 기록 기반 피드백 루프 구조로 구현 완료
- 다음 주 루틴 생성 초기에는 "이전 설정값이 새 입력값을 덮어쓰는" 버그가
  있었으나, 새 입력값을 우선 적용하도록 수정함 (구현 시행착오 참고)

## ADR-3: SQLite 대신 JSON 파일(routines.json) 저장

### 상태
승인됨

### 배경 (Context)
1인 사용 프로젝트에 SQLite 등 별도 DB 설치 및 스키마 관리는 과도한
엔지니어링으로 판단했다.

### 결정 (Decision)
`routines.json` 파일에 `fs.readFileSync`/`fs.writeFileSync`로 루틴과
수행 무게 기록을 읽고 쓴다. 최대 20개까지 저장하며, 초과 시 가장
오래된 항목을 자동 삭제한다.

### 이유 (Rationale)
- 별도 설치 없이 즉시 동작
- 동시 접속이 없는 1인 환경에 충분
- db.ts 모듈로 저장 로직이 분리되어 있어, 필요 시 SQLite로 교체 용이

### 결과 (Consequences)
- 검색/필터, 동시 쓰기 안전성은 SQLite보다 약함 (1인 사용 환경에서는
  허용 가능한 트레이드오프)
- 데이터가 늘어나거나 다중 사용자 지원이 필요해지면 SQLite 등 DB로
  전환 가능 (ARCHITECTURE.md 향후 확장 참고)
